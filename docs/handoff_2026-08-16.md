## 二、唯一未决的技术问题（接着做这个）

**`S4/depth-4/semantic_replay` 的 cross-binding 校验失败**，报
`visible Business SQL calls moved by 0, want 1`。

**根因已查实，不要重查**：Observer 的可见计数条件是
`包含可见关系 AND NOT 包含伴随关系`（`adapter_bindings.go` 的
`businessSQLSnapshotFor`）。不透明快照发布会发**两条**语句（业务行一条、序数伴随一条），
故 S1/S2/S5/S6 的 `business_sql_delta` 是 2；而 **S4 的 Product 是语义 View，Gateway
把它展开、用 CTE 把叶子的序数伴随并进同一条语句，只发一条**。实测那条语句是：

```
with ordinal_sidecar_… as (select linenumber, orderkey, row_handle
  from taskgate_ordinal.provsql_lineitem_v1), ordinal_sidecar_… as (select o…
  calls=2  visible=false  companion=true
```

**没有任何语句提到 `reporting.final_v5_analytics_depth4`。** 所以 S4 的
`business_sql_delta = 1` 全部来自伴随计数，可见恒为 0。**结果确实来自数据库**
（语句就在那里、calls 递增），不是泄漏。

**未完成的改法（我停在这一步）**：让 cross-binding 检查认识执行形状——合并语句形态下
断言「可见与伴随增量之和恰好为 1」，而非「各为 1」。被检验的性质不变（第二个任务确实
向数据库执行了恰好一次），只是匹配 View 的执行方式。**不要用「放宽检查」或「换个伴随
关系凑数」的办法**：`companion == 1` 对单条合并语句结构上不可满足，硬凑就是伪造。

改动位置：`evaluation/cmd/final-v5-adapter/baseline.go` 的 `crossBindingVerification`，
逐条命名的那个循环。判定「是否合并语句形态」的可靠依据是该格的 Product 是否带
`view_contract`（语义 View）而非 `snapshot_publication`。

## 五、必须记住的三个流程陷阱（今天各踩了一次）

1. **Gateway 镜像不会自动重建。** 适配器每跑必重编，但 Compose 镜像只在
   `TASKGATE_REAL_PILOT_BUILD=1` 时重建。**改了 `internal/` 却不带这个变量，等于没改，
   而运行照样成功、照样出数字**——今天差点据此得出「union 修复无效」的假结论。
   凡改动 `internal/` 后的实跑，一律带 `TASKGATE_REAL_PILOT_BUILD=1`。
2. **实跑期间不得修改该运行依赖的任何文件。** 我在 55 格运行进行中改了它正在执行的
   `start-fresh-deployment.sh`，写入的截断窗口让运行读到半截脚本而中止。
3. **创建任何具名产物之前先全仓 grep 这个名字。** 我今天两次「没查权威来源就动手」：
   请作者批准新建 Baseline 专属 Product（已评审 Catalog 候选早有另一套方案，该批准无需
   执行），以及给 S4 建物化视图（`benchmark-v1-generate.sql` 里早有真正的四层视图链，
