# Final V5 contract conflict register

Research design: **AUTHOR_APPROVED_FOR_IMPLEMENTATION**
Exact generated bytes/freeze: **NOT_APPROVED**

This register preserves repository audit facts and distinguishes a settled
author design from an implemented, runnable, or frozen experiment. None of the
items below may be hidden by relabeling a Pilot, accepting partial cell
coverage, inventing a digest, or changing the hash-locked protocol/matrix.

## C2 — Outcome x1 rounding conflicts with the 30-sample schedule

Current executable code uses per-sample nearest-integer-half-up. With one
candidate member, 50% and 90% therefore become one overlapping member in every
sample (100% realized per sample).

Author resolution: measured x1 memberships are exactly 0/15/27/30 across 30
samples at targets 0/50/90/100. x100 and x10k use exact per-sample integer
counts. Seeded selection, per-sample evidence, aggregate validation, and five
domain-separated excluded warmups are fixed by `scale-v1.json`.

Remaining conflict: the existing production Adapter, its legacy vectors and
digests, sample schema/evidence, finalizer, README, and configs still implement
or describe the old rounding. The new independent evaluation Oracle implements
and tests the approved 0/15/27/30 schedule, but does not make the runtime path
ready. Scale capability remains false until the production pieces change
together without changing workload labels.

## C3 — Default Scale seals 60 while capability arithmetic includes 62

The hash-locked workload manifest contains 24 Dependency E2E, 36
Outcome-Merkle, and two separate `scale-extreme` cells. The default Scale
config/final campaign covers 60; extreme execution is separately gated, while
the capability check has required 62.

Author contract: default Scale is explicitly 60. The two kernel-only extreme
cells are retained as a conflict appendix and contribute zero default cells.

Remaining conflict: capability/orchestration/finalizer semantics have not been
reconciled. The appendix cannot be counted as completed default Scale evidence
and cannot be silently deleted from the workload manifest.

## C4 — Protocol prose status and executable capabilities disagree

At audit time `protocol-v1.yaml` described staged source adapters as complete,
while the executable gate reported Baseline=false, Scale=false,
Artifact=false and 6/9 capabilities overall. Changing protocol bytes would
change its hash and every bound config.

Resolution rule: keep the hash-locked protocol bytes unchanged in this contract
stage and record the contradiction here. A future deliberate protocol revision
requires regenerated configs and explicit author review; implementation work
must not treat prose status as capability evidence.

## C5 — Complete Catalog candidate exists but live bindings do not

The current deployment loads one exact `config/catalog.yaml`; compose,
launcher, final binding, and tests do not merge an overlay. The default Catalog
also gives the ProvSQL route only one query and three result rows, insufficient
for Baseline.

Author resolution: `catalog/benchmark-contract-v1.yaml` is a complete Catalog
candidate, not a fragment. It includes the Exposure, Result-heavy, and depth-4
Products plus an implementable generic low-sensitivity benchmark route and
budget; the unrelated `expense_summary` remains on its own exact narrow route.
The candidate passes the strict Catalog loader.

Remaining conflict: all-zero datasource, new-Publication, and View digest
fields are explicit fail-closed sentinels. Live schema, sidecar, dictionary,
manifest, lineage, and the root View-contract component digests have not been generated or
reviewed; compose/launcher/final binding/configs do not select this Catalog.
Thus discovery semantics are specified, but a formal BDG run is not ready.

## C6 — Dependency overlap needed a real 414,000-row Product

The existing frozen lineitem publication has 250,000 rows. It cannot represent
two 207,000-row source sets with zero overlap, whose union is 414,000 rows.
Treating existing as a prefix of candidate would incorrectly make union equal
candidate and would not implement existing=N, candidate=N.

Author resolution: the new 414,000-row `final_v5_exposure_scale` Product uses
candidate `(0,M]` and existing `(M-K,2M-K]`. Each row contributes five
Dependency Facts. S3 reuses the same real Product.

Remaining conflict: the Publication and ordinal artifacts are not generated or
installed. The present adapter also uses the same candidate query for prefill;
at 100% it would cause semantic replay. It must implement the distinct
`sum(metric)` history identity and `count(*)` candidate identity before the
approved overlap contract is runnable.

## C7 — S4 View meaning is settled but live contracts are absent

Filtering above a grouped View is not a safe arbitrary rewrite. The approved
four layers are fixed filter/projection, connected join, aggregate, and root
projection; the outer query only projects the analytical fields.

The source-controlled SQL creates this exact chain. The root now exposes two
distinct public scope fields mapped to the orders and lineitem terminal
`partition_key` fields, while the measured query projects only the three
analytical fields and uses canonical typed-row ordering outside View
composition. The root definition, dependency, canonical-plan, and interface
bindings still require live PostgreSQL generation. The Catalog candidate
therefore carries fail-closed sentinels. No S4 measurement or claim is eligible
until generated contracts match the reviewed chain and terminal bindings.

## C8 — Production result hashing is not the independent Result Oracle

The existing production result hash sorts JSON rows and does not bind the full
ordered SQL schema/type/NULL contract required for Direct/BDG/Parquet
equivalence.

Author resolution: `result-normalization-v1.json` defines an evaluation-only,
typed, length-delimited, ordered SHA-256 identity. The independent Direct-row
hasher, Parquet reader, fixed vectors, and mutation tests now implement that
contract. Remaining conflict: every real adapter path must feed those inputs,
bind the reviewed schema, and compare the independent result rather than use a
production hash as its expected value.

## C9 — SQL probe MD5 is not a binding Dataset fingerprint

`benchmark-v1-probe.sql` emits internal MD5 summaries for practical database
sanity checks. MD5 is not accepted as the Dataset identity.

Author resolution: an evaluation-only typed streaming hasher now binds Product
identity, namespace, snapshot, ordered schema/type/stable-key/collation
metadata, and all 815,000 deterministic rows with SHA-256. Tests prove seed,
Product, type, collation, and value mutations change the digest while retaining
one row at a time. Remaining conflict: its locally regenerated digest has not
been compared with a live PostgreSQL corpus or recorded in an author-reviewed
Dataset Binding. The SQL probe output may accompany that evidence but cannot
replace it.

## C10 — Generated artifacts, configs, campaign, and paper remain open

## C11 — Result-heavy HOT artifacts exceed the Gateway activation boundary

Resolved under `final-v5-contracts-v1.1`: the Result-heavy Dataset Generator
now materializes, the `final_v5_result_heavy` Product and the
`final-v5-result-heavy-v1` Publication are wired into the live Compose stack,
Business PostgreSQL, the ordinal sidecar installer and `config/catalog.yaml`,
and the Contract-to-Runtime Bridge binds all six Artifact cells to that live
Catalog with generated (non-sentinel) digests.

Remaining conflict: the Gateway refuses to activate the resulting Catalog.
`cmd/gateway/snapshot_loader.go` enforces a deployment-wide 160 MiB HOT
artifact activation boundary, and the live publications now total 233.4 MiB:

| Publication | HOT bytes |
| --- | --- |
| `final-v5-result-heavy-v1` | 126,813,361 (120.9 MiB) |
| `provsql-lineitem-v1` | 101,004,070 (96.3 MiB) |
| `provsql-orders-v1` | 16,603,206 (15.8 MiB) |
| `provsql-nonce-v1` | 262,487 |
| `expense-detail-v1` | 16,638 |
| `expense-summary-v1` | 9,488 |
| **total** | **244,709,250 (233.4 MiB)** |
| boundary | 167,772,160 (160.0 MiB) |

The 100,000-row, sixteen-field Publication alone is 120.9 MiB, so it fits
beside the expense Publications (121.0 MiB total) but not beside the frozen
ProvSQL corpus. The reviewed Catalog candidate additionally declares
`final_v5_exposure_scale`, which would add more.

This is a production limit, not a test artifact, and it is deliberately not
bypassed. Resolving it is an author decision because each option changes
something the paper reports:

- raising `maxGatewayHotArtifactsBytes` changes a published V4 architectural
  threshold and the 512 MiB Gateway memory story;
- giving the Artifact profile its own activated Catalog subset changes what
  "the live production Catalog" means for that profile;
- changing the Result-heavy Publication to a cold-only or handle-only sidecar
  changes the Publication design the Oracle and Receipts bind to.

Until it is resolved no Artifact cell can execute against a running Gateway,
so `artifact` remains `false` and the capability report remains `6/9`.

## C12 — Profile activation needs a per-profile snapshot artifact directory

Found by the Stage B.2a-Live activation smoke against a real deployment.

`cmd/gateway/snapshot_loader.go` requires the snapshot artifact directory to
contain exactly the publications the active Catalog declares. It rejects an
extra directory with `snapshot artifact directory contains undeclared
publication`. That check is correct and must not be relaxed.

The shared `snapshot-index-artifacts` volume holds all six compiled
publications, because one compiler pass builds them all. A profile Catalog
declares only its own closure -- `final-v5-result-heavy-v1` for the
result-heavy profile -- so a Gateway started on that Catalog against the shared
volume fails closed on the other five directories:

    load: snapshot artifact directory contains undeclared publication
          "expense-detail-v1"

Activating a profile therefore requires swapping the artifact directory as well
as the Catalog: `GATEWAY_SNAPSHOT_ARTIFACT_DIR` must point at a directory
holding exactly the closure's publication bundles. Swapping only the Catalog is
not sufficient, and no profile has been activated yet for this reason.

This is a deployment-layer gap, not a contract change: contract v1.2 already
says a Catalog-bound instance activates one closure at a time. Resolving it does
not alter the profile unit, the closure digests, the HOT ceiling or any Oracle.

## C13 — Cross-profile semantic replay cannot be tested with the current profiles

The persisted semantic-replay isolation test requires one logical query that is
legal under two different live-route profiles. The seven Catalog-and-route
cleared profiles have pairwise disjoint Product closures:

| profile | Products |
| --- | --- |
| result-heavy | `final_v5_result_heavy` |
| provsql-nonce-join | `provsql_orders`, `provsql_lineitem`, `provsql_nonce` |
| expense-detail | `expense_detail` |
| attack-expense-detail | `final_v5_attack_expense_detail` |
| concurrency-expense-detail | `final_v5_concurrency_expense_detail` |
| rls-unlimited | `final_v5_rls_unlimited_expense_detail` |
| rls-bounded | `final_v5_rls_bounded_expense_detail` |

Five of them share the Publication `expense-detail-v1`, but each exposes it
through a different Product, so a query legal under one is refused by another by
construction. No pair admits the same logical query, and the test is therefore
`SEMANTIC CACHE ISOLATION TEST BLOCKED`.

Comparing digests across profiles is explicitly not accepted as a substitute.
Resolving this needs either a reviewed profile pair that shares a Product, or an
author decision that cross-profile replay isolation is proven some other way.

No generated digest is frozen by this register. A generated value first becomes
a `REVIEW_CANDIDATE`; only explicit author review may change its status to
approved/frozen. Until every conflict required by a claim is resolved,
Baseline, Scale, and Artifact remain false and the formal Campaign remains
closed.
