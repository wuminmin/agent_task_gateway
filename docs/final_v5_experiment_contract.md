contract binds `workloads-v1.yaml` SHA-256

could be mistaken for a digest.

## Dataset and Product contract

S1, S2, S4, and S5 reuse the existing frozen `provsql_orders` and
`provsql_lineitem` Products and Publications. `SF1` and `SF10` are query
thresholds `orderkey <= 5000` and `orderkey <= 50000` over the same frozen
50,000-order corpus. This contract creates no fictitious 500,000-order SF10
corpus. The existing `provsql_nonce` Product/Publication remains available for
the separate registered ProvSQL experiment; S2 does not add a nonce join.

S3 and Dependency Scale use a new real source-controlled Product:

- Product: `final_v5_exposure_scale`
- Publication: `final-v5-exposure-scale-v1`
- snapshot: `final-v5-exposure-scale-2026-v1`
- namespace: `final_v5.exposure_scale`
- stable role: `final_v5_exposure_scale`
- entity key: `member_rank`
- fields: `member_rank bigint`, `metric numeric`, `family_id integer`, and
  `partition_key integer`
- deterministic rows: `member_rank=1..414000`, constant family/partition 1,
  and the reviewed numeric metric formula in `benchmark-products-v1.json`.

Each retained Exposure row contributes one base-row Fact plus four predicate
field Facts (`member_rank`, `metric`, `family_id`, `partition_key`), exactly
five Dependency candidate Facts per row. That enumeration order is for audit
vectors only; set canonicalization sorts member identities. This is a real
publication namespace, not an evaluation-only fictional Product.

S6 and Artifact share a new `final_v5_result_heavy` Product and
`final-v5-result-heavy-v1` Publication with exactly 100,000 deterministic
rows. The x16 ordered schema is:

`row_id, category, amount, event_date, sequence_no, approved,
event_timestamp, description, quantity, unit_price, tax_amount, settled_date,
processed_at, region, revision, active`.

The x4 projection is exactly its first four fields. Text fields bind the
attested PostgreSQL `en_US.utf8` collation with version `2.36`. Dataset
generation must fail if the live collation version differs.

The SQL probe's internal MD5 values are database sanity checks only. They are
not the binding Dataset fingerprint. The binding fingerprint is an
evaluation-only, typed, streaming SHA-256 over reviewed schema metadata and
all ordered Product rows. Formula regeneration now produces a deterministic
source-derived reference digest; the matching live PostgreSQL observation and
author-reviewed Dataset Binding remain ungenerated and unapproved.

The default Catalog is not edited. The source-controlled
`evaluation/final-v5-wsl2/catalog/benchmark-contract-v1.yaml` is a complete,
directly parseable Catalog candidate, not a merge overlay. It exposes the two
new terminal Products and the semantic Product to Catalog/OA. A generic
low-sensitivity benchmark route supports every registered benchmark Product
subset; `expense_summary` remains on an exact narrow route so it cannot inherit
the benchmark budget. Its all-zero datasource,
new-Publication, and View digest values are deliberate fail-closed sentinels;
live generated review candidates must replace them before runtime use. The
exact candidate digest must then be bound through the launcher, final binding,
and configs. The default Catalog remains unchanged.

## Baseline query contract

- **S1:** two-column ordered scan of `provsql_orders` at the 5,000/50,000
  thresholds.
- **S2:** connected orders--lineitem inner equijoin, grouped by `status`, with
  `sum(extendedprice)` and `count(*)`. Direct and BDG use identical data and
  parameters. The frozen query defines no total result order and does not rely
  on returned row order; the independent normalizer sorts complete typed row
  encodings before hashing. This is also the common frozen data basis for the
  separately registered ProvSQL comparison.
- **S3:** one-column ordered `member_rank` result over prefixes of 1,000,
  10,000, and 45,000 Exposure rows. The exact release/dependency candidate
  counts are 1,000/5,000, 10,000/50,000, and 45,000/225,000. The four predicate
  atoms plus their composite produce five Outcome candidates.
- **S4:** the semantic Product has exactly four live PostgreSQL View layers:
  fixed filter/projection (`orderkey <= 5000`), connected join, aggregate, and
  root projection. The root also exposes separate orders/lineitem partition
  scope fields so governance can prove both terminal scopes; the outer query
  projects only the three analytical fields and does not filter, order, or
  aggregate above the barrier. Canonical typed-row ordering supplies result
  determinism. The root View-contract components require live generation and
  review.
- **S5:** Direct uses SQL `UNION DISTINCT`. BDG uses the callable SDK
  `execute_plan` structured-union entrypoint, never the plain SQL entrypoint.
  The right branch is the exact 2,500/25,000-row subset of the 5,000/50,000-row
  left branch. Relational `ORDER BY` is outside that production fragment, so
  both drained results use canonical typed-row ordering before hashing.
- **S6:** the six result-heavy cells use 100/10,000/100,000 rows at x4 and x16.

Direct and BDG timing begins immediately before the arm query call and ends
after complete logical-result drain. Product generation, probes, OA/task
provisioning, oracle work, and five deterministic warmups are excluded. Thirty
samples are retained per cell, including failed or invalid samples.

## Scale contract

For Dependency Scale, let `M=N/5` source rows and `K=M*p/100` for overlap
percentage `p`. Candidate source keys are `(0,M]`; existing/history keys are
`(M-K,2M-K]`. Therefore each side contains exactly `N` Dependency Facts,
intersection is `5K`, candidate-novel is `N-5K`, and union is `2N-5K`.
At the largest zero-overlap cell the union spans all 414,000 source rows.

The three `(M,N)` pairs are `(2,000,10,000)`, `(20,000,100,000)`, and
`(207,000,1,035,000)`. History uses `sum(metric)` while candidate uses
`count(*)`, with the same dependency fields. Distinct normalized query
identities are required so the 100% dependency-overlap novel cell is not
mistaken for semantic replay. The current adapter does not yet implement this
history/candidate identity protocol; Scale remains not runnable.

For Outcome-Merkle controls, the target is realized over 30 measured samples.
For x1, exactly 0/15/27/30 memberships overlap at 0/50/90/100%. For x100 and
x10k, every measured sample has 0/50/90/100 and
0/5,000/9,000/10,000 overlapping members respectively. Seeded membership
selection is deterministic. Five warmups use a separate domain and are
excluded. These cells are control-physical-representation measurements, not
Full-BDG latency.

## Artifact and normalization contract

Each Artifact cell must match the corresponding Baseline S6 Product,
Publication, rendered query, projection, ordered typed schema, rows, and
canonical logical-result SHA-256. The measured Parquet must be produced by the
real BDG path and parsed back through the same evaluation-only normalizer.
Runtime Parquet and ciphertext digests/byte sizes are observations; they are
not predeclared oracle values, and an oracle may not create or inject the
measured file.

Logical schema and results use domain-separated, uint64-big-endian
length-delimited encoding, explicit type and NULL tags, a registered total
ordering mode, and SHA-256. Query-order workloads commit their stable-key SQL
order; S2/S4/S5 sort complete canonical typed-row encodings bytewise outside
the measured query. Duplicate rows are retained. Production `result_sha256` is
evidence to compare against the independent oracle, never the source of
expected data.

## Independent-oracle and freeze rule

Result, Dependency, Outcome, and Artifact oracles live under an import-denied
evaluation boundary. They may read reviewed contracts, deterministic formulas,
read-only PostgreSQL results, and emitted Parquet, but may not import or call
production exposure/root/query/Receipt implementations or reuse production
digests as expected values. One canonical manifest is required per default
cell: 58 + 60 + 6 = 124 manifests.

The implementation may prepare review candidates, but no generated digest is
frozen until authors review the exact Dataset, Publication/sidecar, Catalog
candidate, View contracts, query templates, normalization bytes, 124 oracle
manifests, private configs, and final commit together. Until that point
Baseline, Scale, and Artifact capability gates remain false and no final paper
number may be written.
