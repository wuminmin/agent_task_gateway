Budget-Constrained Query Processing for Autonomous Database Agents}

\author{Anonymous Author(s)%
\thanks{The artifact includes a controlled local PostgreSQL performance

\begin{abstract}
Autonomous database agents issue adaptive sequences of queries and may delegate
subtasks to other agents. Conventional access control bounds each query but does
not directly bound how many distinct facts an authorized task accumulates across
rewrites, pagination, retries, and delegation. We present TaskGate, a prototype
for task-bound exposure accounting. A versioned fact identity binds a data
product, snapshot, entity key, field, and value version. Each human-authorized
root task maintains separate release and source-influence ledgers, preventing a
small aggregate result from hiding a large contributing input. The online path
executes a visible query and provenance companion in one read-only snapshot,
buffers the result, derives its fact sets, and atomically settles only facts
novel to the root task before release. Signed delegation preserves the same
ledger. We define compositional semantics for a positive relational fragment
with grouping and four aggregates, implement an exact dual-budget representation
planner, and check a finite ledger model. A deterministic artifact validates
ground truth, 1,024 unique PostgreSQL-checked rewrites, anti-arbitrage cases,
and planner oracles. Across three local trials and 31,296 measured operations,
a warm full-path history hit has 12.1-ms median and 14.2-ms p95 latency at one
worker; at eight workers p95 rises to 70.5~ms as root-ledger lock p95 reaches
40.5~ms. On 120 externally scored four-part agent-task traces, exact planning
achieves 60\% task success versus 40\% for utility-greedy selection, with no
budget violation.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

\IEEEPARstart{D}{atabase} authorization answers whether a principal may execute
a particular operation. An autonomous agent creates a second problem: during a
single human-approved task it can adaptively issue many individually legal
queries. It can split a projection, overlap pages, retry with a new request
identifier, ask an equivalent query, or delegate a narrower subtask. Per-query
authorization and row limits do not state how much distinct data the resulting
task family has learned.

Counting queries is insensitive to answer size. Counting returned rows makes a
one-row aggregate appear cheap even when it depends on millions of source rows.
Counting bytes or cells varies with encoding and query shape. Monetary query
pricing has developed formal anti-arbitrage objectives
\cite{koutris2012query,deep2017qirana,peng2025aria}, while provenance explains
where results came from \cite{green2007provenance,amsterdamer2011aggregate}.
Our question is narrower and operational: how can a human authorization create
a stateful, explicit-disclosure budget that remains conserved while database
agents query and delegate?

\system treats the root task as the budget subject. A result has two effects.
\emph{Release exposure} identifies values actually delivered. \emph{Source
influence} identifies positive source facts that affected selection, joining,
grouping, or aggregation. The latter prevents a count from being accounted as
one input fact merely because it returns one cell. Both effects are sets, so a
fact already known anywhere in the task family has zero incremental charge.

The system follows a withhold-before-settlement discipline:

\begin{center}
\small
\code{reserve -> execute/buffer -> derive -> settle -> release}.
\end{center}

The visible query and its provenance companion observe one PostgreSQL snapshot.
The gateway releases neither until a control-database transaction has inserted
novel facts, checked both root limits, settled resource use, stored the encrypted
result, and persisted audit and receipt evidence. A failed limit check rolls the
transaction back while the business execution remains separately measurable.

This paper makes four implementation-backed contributions:

\begin{enumerate}
\item A dual exposure effect over a restricted positive relational algebra,
including projection, selection, join, union, pagination, grouping, and
\code{COUNT}/\code{SUM}/\code{MIN}/\code{MAX}.
\item An online paired-snapshot algorithm and a PostgreSQL root-family ledger
whose settlement charges exactly novel facts and withholds over-budget results.
\item Signed, monotonic multi-agent delegation that shares root knowledge, plus
an overlap-aware exact selector for choosing server-executed representations
under two set-valued budgets and a fixed measurable utility profile.
\item Executable ground truth, rewrite and anti-arbitrage tests, a finite TLA+
model, a repeated full-path PostgreSQL overhead campaign, and externally scored
budget-constrained agent-task traces.
\end{enumerate}

The implementation does \emph{not} claim arbitrary SQL equivalence, differential
privacy, or inference control. The online compiler currently accepts one-product
structured plans; join and union exist in the executable algebra but are not yet
connected to online provenance. These boundaries are part of the result, rather
than hidden behind a broad ``SQL support'' label.

\section{Context and Related Work}
\label{sec:related}

\subsection{History-Based Query Auditing and Inference Control}

Database auditing has long treated a query log, rather than an isolated query,
as the security object. Hippocratic-database auditing reconstructs which logged
queries accessed protected data \cite{agrawal2004hippocratic}, while batch SQL
auditing asks whether a sequence of answers determines a forbidden view
\cite{motwani2008auditing}. Online auditors decide whether to answer the next
query: early work studies Boolean attributes \cite{kleinberg2003auditing},
simulatable auditing prevents the accept/deny bit itself from leaking the secret
\cite{kenthapadi2005simulatable}, and robust auditing analyzes partial versus
full disclosure under aggregate queries \cite{nabar2006robustness}.

The broader inference-control literature models integrity constraints,
inference channels, and accumulated disclosures \cite{brodsky2000secure}, and
surveys attacks that combine answers with external knowledge
\cite{farkas2002inference}. Query--view disclosure analysis further formalizes
collusion and partial information release \cite{miklau2004formal}. These results
rule out a broad ``history makes querying safe'' claim. \system is deliberately
narrower: it neither models an adversary's prior knowledge nor protects against
negative answers, denial leakage, or implicit logical inference. It meters a
contract-declared set of positive facts, and its history is one signed root task
and all descendants rather than a global user history. Simulatable or
knowledge-aware inference control is complementary and could sit outside the
gateway.

\subsection{Query Pricing and Privacy Accounting}

Query-based pricing derives monetary prices from priced views and studies
arbitrage induced by query determinacy \cite{koutris2012query}. QIRANA extends
scalable, history-aware pricing to a broad SQL class including aggregation
\cite{deep2017qirana}; ARIA uses tuple information gain for linear-time pricing
of SPJA and simple aggregate queries \cite{peng2025aria}. Thus attribute
weighting, history-aware charging, and rewrite resistance are not new by
themselves. \system instead treats price as an admission budget over explicit
contract facts, scopes state to a task family, and withholds delivery when the
atomic settlement fails.

History also matters in differential privacy systems. CacheDP reuses past noisy
answers to reduce privacy spending \cite{mazmudar2022cachedp}, and DProvDB tracks
privacy loss by analyst provenance \cite{zhang2023dprovdb}. These systems reason
about randomized mechanisms and privacy composition
\cite{dwork2014foundations}. \system releases exact answers and therefore offers
no $\epsilon$-DP guarantee; its budget bounds only facts recognized by the
active exposure profile.

\subsection{Provenance Foundations and Systems}

Why- and where-provenance identify contributing data and output locations
\cite{buneman2001why}, while lineage traces warehouse outputs back through
transformations \cite{cui2001lineage}; Cheney et al. survey the resulting
database-provenance design space \cite{cheney2009provenance}. Semiring
provenance provides compositional annotations for positive relational queries
\cite{green2007provenance}, and aggregation requires value-level treatment
beyond tuple annotations \cite{amsterdamer2011aggregate}.

Provenance is also an implemented database capability. Perm and GProM compile
provenance questions through query rewriting \cite{glavic2009perm,arab2018gprom};
ProvSQL adds provenance and probability to PostgreSQL
\cite{senellart2018provsql}; and Smoke integrates fine-grained lineage into
operators for interactive performance \cite{psallidas2018smoke}. \system claims
neither a new provenance algebra nor a general provenance engine. It specializes
provenance to two set-valued effects---facts explicitly released and base facts
that positively influence them---then requires answer/effect co-generation in
one snapshot and atomic settlement before release. Multiplicity, negation, and
general recursive SQL remain outside the current online profile.

\subsection{Usage Control, Delegation, and Quotas}

Usage control extends authorization across an ongoing use and permits mutable
attributes and obligations \cite{park2004ucon}; execution-history access
control likewise makes past actions part of authorization
\cite{abadi2003history}. Delegation has mature logical and role-based
foundations \cite{li2003delegation,barka2000delegation}, while macaroons provide
cryptographic attenuation through contextual caveats
\cite{birgisson2014macaroons}. Consumable credentials encode bounded use in
linear logic \cite{bowers2007consumable}; distributed storage quotas use
reconcilable vouchers \cite{pollack2007quota}; and PERMIS combines delegated
authorization with history-sensitive cumulative-resource decisions
\cite{chadwick2008permis}.

Consequently, neither token attenuation, delegation depth, consumable authority,
nor quota accounting is claimed independently. \system's narrower systems claim
is that every descendant settles the same semantic disclosure effect against a
single root-task exposure ledger, so delegation cannot mint a fresh disclosure
budget. The prototype uses centralized transactional settlement; distributed
vouchers and reconciliation would require an additional safety argument.

\subsection{Database Policy Enforcement and Agents}

Database-backed policy systems rewrite or validate queries against application
policy \cite{mehta2017qapla,zhang2022blockaid}. Natural-language database work
initially emphasized text-to-SQL accuracy on cross-domain schemas
\cite{yu2018spider} and then larger realistic databases
\cite{li2023bird}. AgentBench includes database operation among interactive
agent environments \cite{liu2024agentbench}; D-Bot applies a multi-agent system
to database diagnosis \cite{zhou2024dbot}; and Spider~2.0 evaluates enterprise
workflows involving multiple queries, metadata, and dialects
\cite{lei2025spider2}. Recent security work aligns natural-language interfaces
with database access policy \cite{liu2026safenlidb}, measures indirect prompt
injection against tool-using agents \cite{debenedetti2024agentdojo}, and applies
runtime data-flow control to agents \cite{summers2026dataflow}.

These systems motivate treating generated SQL and agent tools as untrusted, but
they pursue complementary targets: generation quality, operational assistance,
per-request policy, prompt-injection resilience, or information-flow labels.
\system places the model outside the trusted computing base and focuses on
cumulative, explicit database disclosure across retries, pagination, supported
rewrites, and delegation.

\textbf{Novelty boundary.} History, inference control, pricing, provenance,
query mediation, delegation, and quotas are all established separately. The
claim evaluated here is their enforcement composition: a typed,
contract-defined release/influence effect generated beside the answer in the
same database snapshot, exact novel-set settlement against one root task-family
ledger before delivery, and invariance over the supported rewrite and delegation
closure. This boundary is narrower than general SQL noninterference and stronger
than stateless authorization for the modeled positive-disclosure threat.

\section{Exposure Model}
\label{sec:model}

\subsection{Facts and Task State}

V2 treats a FactID as a semantic object and its SHA-256 as only a database
index.  Let $\nu$ be a catalog-owned source namespace (not a view alias), $s$
an immutable snapshot, $e$ a stable entity key, $a$ a field ID, $\tau$ a
PostgreSQL type, and $\operatorname{canon}_\tau(v)$ its canonical value.  Base identities are

\begin{align}
 f_{row}&=\langle\pi,\nu,s,e\rangle,\\
 f_{cell}&=\langle\pi,\nu,s,e,a,\tau,\operatorname{canon}_\tau(v)\rangle .
 \label{eq:fact}
\end{align}

A derived identity is
$f_d=\langle\pi,\mathcal S,k_o,N_\pi(x),\tau,\operatorname{canon}_\tau(v),H(W)\rangle$,
where $\mathcal S$ is a sorted snapshot bundle, $k_o$ is the canonical output
row key, $N_\pi(x)$ erases aliases and normalizes the supported expression, and
$W$ is a base-fact witness multiset. The durable key is
$\mathrm{SHA256}(\texttt{TASKGATE-FACT-V2\textbackslash0}\|\operatorname{Canon}(f))$.
Control PostgreSQL stores $\operatorname{Canon}(f)$ and compares it on every hash conflict;
a same-hash, different-payload row aborts the transaction. V1 and V2 tagged
payloads are disjoint and one root ledger fixes exactly one profile.

\begin{theorem}[Fact identity well-definedness]
For every value in the V2 supported PostgreSQL type domain, canonical encoding
is deterministic and injective over the typed semantic payload.
\end{theorem}
\begin{proof}[Proof sketch]
Every component is type tagged and length delimited; lists are cardinality
prefixed and canonically sorted. Integers and exact numerics use unbounded
integer/rational normal forms, timestamps use the profile timezone, and NULL
has its own token. Tuple injectivity follows by unique decoding.
\end{proof}

\begin{definition}[Exposure effect]
For query $q$ over snapshot $D_s$, the effect
$\effect(q,D_s)=\langle \facts_r,\facts_i\rangle$ contains release facts
$\facts_r$ and source-influence facts $\facts_i$ under a versioned profile
$\pi$.
\end{definition}

Every root task $T$ stores known sets
$\known_T=\langle\known_T^r,\known_T^i\rangle$ and limits
$B_T=\langle B_T^r,B_T^i\rangle$. Settlement computes

\begin{align}
 \Delta_T^r(q) &= \facts_r(q,D_s)\setminus\known_T^r,\\
 \Delta_T^i(q) &= \facts_i(q,D_s)\setminus\known_T^i.
 \label{eq:delta}
\end{align}

V2 measures cardinality independently in each dimension. A query may settle
only if
$|\known_T^r|+|\Delta_T^r|\leq B_T^r$ and
$|\known_T^i|+|\Delta_T^i|\leq B_T^i$.

\subsection{Annotated Relations}

The complete core grammar is
\begin{align*}
e ::= {}& \operatorname{Scan}[\nu,s,r,\Gamma]
 \mid \sigma_{p;F}(e) \mid \pi_A(e) \mid e\bowtie_{\Theta}e \\
 &\mid e\cup_\delta e \mid \gamma_{G;\mathcal A}(e)
 \mid \operatorname{Page}_{O,K,o,l}(e),
\end{align*}
where $\Theta$ is a nonempty conjunction of same-typed equalities,
$\mathcal A\subseteq\{\code{COUNT(*)},\code{COUNT},\code{SUM},\code{MIN},
\code{MAX}\}$, and $O$ extended by stable key $K$ is a total order.  The
typing rules require disjoint role-qualified join schemas, identical typed
union schemas, existing predicate/group/aggregate fields, PostgreSQL-correct
aggregate output types, nonnegative page bounds, and exact deterministic
collation name/version bindings for collatable fields.  An ill-typed node is
rejected rather than assigned an effect.

An intermediate row stores $\langle k,v,S_r,W_r,S_a,W_a\rangle$: row support
$S_r$ and witness $W_r$, plus per-cell support sets $S_a$ and witness
multisets $W_a$.  Each relation field also carries a data-independent
canonical lineage expression: scans bind it to the namespace-qualified field,
unary operators propagate it, grouping composes it, and union canonicalizes the
sorted child expressions.  The representation invariant is
$\operatorname{support}(W_r)=S_r$ and
$\operatorname{support}(W_a)=S_a$; all support members are snapshot-covered V2
base facts.  Ordinary proof composition adds multiplicities ($\oplus$), while
alternative proofs under union-distinct use pointwise maximum ($\sqcup_{max}$).
Support drives the influence ledger, while multiplicity in $W_a$ distinguishes,
for example, three-way from five-way join fanout in a derived identity.
Table~\ref{tab:operators} summarizes the implemented positive fragment.

For a derived aggregate, the release fact uses a canonical expression such as
\code{sum(expense.amount)}, independent of its output alias. Its witness
commitment hashes sorted $(\mathrm{FactHash},\mathrm{multiplicity})$ pairs. Thus equal sums
from different contributors remain different disclosures, while alias changes
do not manufacture a new fact.

The executable rules are as follows.  Scan gives each row the singleton
existence fact and each cell its singleton typed cell fact.  Selection retains
only SQL \code{TRUE} rows and adds all predicate-field annotations to row
support. Projection copies selected annotations.  A conjunctive join emits a
pair only when every equality is \code{TRUE}; \code{FALSE} and \code{UNKNOWN}
both exclude it.  Its row key hashes the sorted identities
$H(\Gamma,\mathcal S,k)$ of its two immediate inputs, which closes Join over
Group, Union, Page, and nested Join results.  Union-distinct partitions typed
tuples by \code{IS NOT DISTINCT FROM}, unions support, and combines alternative
witnesses with $\sqcup_{max}$; hence $W\sqcup_{max}W=W$. Its schema-level
lineage expression is likewise sorted and idempotent, so a downstream Group
cannot observe union operand order through an arbitrarily chosen first row. Grouping uses the
same NULL-equality relation, sums member witnesses, and accepts only a complete
PostgreSQL aggregate-result oracle. Observation unions row support and visible
cell support, and materializes a derived FactID only when no identical existing
release FactID can be reused.

\begin{theorem}[Representation closure]
If the V2 typing judgment derives $\Pi;D\vdash e:\Gamma$ and evaluation
returns $R$, every row of $R$ satisfies the equal-support invariant, has a
unique canonical key, and is a valid input to any well-typed parent operator.
\end{theorem}
\begin{proof}
By structural induction. Scan establishes singleton equal support. Select,
Project, and Page copy or union equal-support annotations. Join uses disjoint
schemas and immediate child identities, so its key construction applies to
every child operator; $\cup$ and $\oplus$ preserve equal support. Union creates
one typed-tuple class key and uses $\cup/\sqcup_{max}$ on the same domains.
Group creates one key per \code{IS NOT DISTINCT FROM} class and uses
$\cup/\oplus$. The implementation checks the full invariant at every operator
boundary.
\end{proof}

\begin{theorem}[Effect determinism]
Fixed $q$, snapshot bundle $D_s$, and V2 profile $\pi$ uniquely determine
$\effect_\pi(q,D_s)$.
\end{theorem}
\begin{proof}[Proof sketch]
PostgreSQL major version, bag, NULL, aggregate, exact collation name and actual
version, UTC, and numeric rules are profile fixed; volatile expressions are excluded. Induction over scan,
selection, projection, equijoin, union-distinct, grouping, and stable pagination
shows that each annotation and output identity is a deterministic function of
its children.
\end{proof}

\subsection{Conservation Properties}

The following properties apply only to the operators and rewrites stated here.
They are not claims about all semantically equivalent SQL.

\begin{property}[Normalization]
Fact-set normalization is deterministic, idempotent, and commutative under
merge.
\end{property}
\begin{proof}[Proof sketch]
Every validated FactID maps deterministically to a digest key. Normalization is
map insertion followed by lexical key order; merge is set union. The three
properties follow from set union and deterministic serialization.
\end{proof}

\begin{theorem}[Restricted projection/selection invariance]
Selection followed by a projection that retains every predicate and output
field has the same effect as the corresponding projection followed by
selection. Reordering projected fields also preserves the normalized effect.
\end{theorem}
\begin{proof}[Proof sketch]
Both plans retain the same keyed rows. Projection copies cell sources and row
lineage; selection adds the same predicate sources to retained lineage. Release
and influence are sets, so traversal and field order disappear on
normalization. The executable corpus checks both target predicates and field
orders for a fixed seed.
\end{proof}

\begin{theorem}[Typed normal-form soundness]
For admissible profile $\Pi$ and snapshot bundle $D$,
\[
 NF_\Pi(q_1)=NF_\Pi(q_2)\Longrightarrow
 \effect_\Pi(q_1,D)=\effect_\Pi(q_2,D).
\]
This implication is not a completeness claim for arbitrary equivalent SQL.
\end{theorem}
\begin{proof}
The typed normalizer can erase only aliases, conjunction/set traversal order,
join operand and predicate order, union operand order, an identical duplicate
union branch, and alternate spelling of the same stable page suffix. Alias is
absent from derived expressions. Set normalization removes traversal order.
Join hashes sorted child identities and uses commutative $\cup/\oplus$.
Union classes are operand independent and $\sqcup_{max}$ is commutative and
idempotent; an identical materialized fact is retained, and relation-level
union expressions are sorted before any downstream composition. Group keys and witness
commitments are sorted. The SQL compiler emits the same catalog-canonical page
suffix represented by the normal form. Each atomic rewrite therefore preserves
Effect; structural induction over well-typed contexts proves the result.
\end{proof}

\begin{theorem}[Split/page/join conservation]
Merging observations for disjoint projections or a complete page partition
equals observing the combined result. Overlapping pages and repeated terminal
observations charge each FactID at most once; join fanout changes witness
multiplicity but not the union of influence support.
\end{theorem}
\begin{proof}[Proof sketch]
Projection and page preserve the identities attached to selected cells and
rows. Merging is set union, for which duplicate membership has no additional
cardinality. Durable request replay does not invoke execution or settlement.
\end{proof}

V2 uses \code{taskgate-query-normal-form-v3}. Besides the rewrites above it
binds namespace, snapshot, lineage digest, canonical SQL types, collation
names/versions, PostgreSQL three-valued bag semantics, UTC, and exact numeric
mode. It deliberately performs no outer-join, arithmetic, window, subquery, or
general SQL equivalence reasoning.

\section{Online Accounting}
\label{sec:online}

\subsection{Compilation and Paired Execution}

An exposure-enabled grant accepts a one-product structured plan. The compiler
first validates visible fields, filters, grouping, ordering, limit, and one of
four aggregates. It then produces two SQL statements. For ungrouped output,
both statements use the same hidden projection, entity-key tie-breaker, and row
ceiling; the gateway also checks their key sets before settlement. For grouped
output, the companion selects entity keys, mandatory scopes, visible and
predicate fields, grouping fields, and aggregate inputs, and requests one row
beyond its evidence ceiling to detect truncation. Both statements pass the same
PostgreSQL AST authorization and scope-injection policy.

The connector executes both statements in one explicit read-only
\code{REPEATABLE READ} transaction \cite{postgres16transaction}. This prevents
a concurrent update from making output and provenance refer to different
database states. The connector reports business and provenance execution time
separately, while resource settlement charges their total. Truncation of the
provenance result is a hard error.

\subsection{Atomic Settlement}

For a successful V2 planning call, the gateway performs the following steps:

\begin{enumerate}
\item Authorize every candidate plan, then execute and buffer every visible and
provenance pair in one Business PostgreSQL \code{REPEATABLE READ} snapshot.
\item Derive exact candidate effects and output-contract utility from the
executed schema and truncation state; no client cost, utility, or weight is
accepted.
\item In Control PostgreSQL, lock the query reservation and root ledger, reload
the latest known sets, and run the overlap-aware exact planner.
\item Insert the selected candidates' release and influence union with a primary key on root, ledger
kind, and fact hash; conflicts contribute zero novel facts.
\item Conditionally increment both used counters only if both limits remain
valid.
\item In the same transaction, settle query/row/database-time resources, store
the encrypted result, append terminal audit evidence, and persist a signed
receipt.
\item Persist the candidate/effect digests, selected set, union-effect digest,
encrypted selected results, terminal audit, and V5 receipt.
\item Commit, discard unselected buffers, and only then return selected results.
\end{enumerate}

If Step 4 affects no row, the transaction returns an exposure-budget error.
Fact inserts and result storage roll back, and the caller never receives the
buffer. PostgreSQL row locking serializes concurrent children at the shared
root. Unique fact keys make charge equal to successful novel inserts, rather
than a count computed before a race.

Let $n$ be the number of unique candidate source and release references in one
observation. Hashing is linear in encoded input size and normalization sorts at
most $n$ hashes, giving $O(n\log n)$ in-memory work and $O(n)$ memory. Ledger
inserts are chunked; index maintenance adds database-dependent
$O(n\log |\known_T|)$ work under a conventional balanced index model. These are
complexity bounds, not measured latency claims.

\subsection{Receipts and Failure Semantics}

A V5 Ed25519 receipt binds all candidate summaries, selected candidates,
planner version, snapshot bundle, union effect, root task, profile, and actual and charged counts in
both dimensions, and the SHA-256 of the normalized observation, in addition to
authorization, datasource, resource budget, result, and audit evidence. It does
not expose raw values or FactIDs.

Failures before connector invocation release both reservations. Ambiguous
connector outcomes conservatively charge the ordinary resource reservation but
release exposure because no result can be delivered before successful
settlement. A process restart applies the same rule. Terminal request replay is
observational: it returns the first persisted status or result and never starts
a second execution.

\section{Delegation and Planning}
\label{sec:planning}

\subsection{Root-Family Conservation}

A child authorization signs both \code{root_task_id} and
\code{parent_task_id}. Its human subject, catalog, datasource, schema, and
profile remain fixed, while products, columns, scopes, sensitivity, expiry, and
all budget dimensions may only narrow. Every execution revalidates the signed
parent grant and active ancestor chain.

All descendants resolve to one root ledger. If a parent and child request the
same fact, only the first successful settlement inserts it. Revoking the root
blocks new descendant queries, while an already terminal request ID remains
readable. Consequently, creating agents or task nodes cannot create fresh
exposure capacity. A child that signs a lower exposure ceiling may add novel
facts only while the shared family total remains within that ceiling; a
zero-novelty replay remains admissible.

\begin{theorem}[Atomic budget safety]
After any committed settlement sequence, each root ledger equals the union of
the novel charges of its settled family queries, and neither cardinality
exceeds its root limit.
\end{theorem}
\begin{proof}[Proof sketch]
All family settlements lock the same root row. The unique fact key admits one
first insert for each root/kind/hash tuple. A transaction adds exactly its
successful inserts to the counters, checks both limits, and otherwise rolls
back. Induction over the resulting serial commit order establishes the union
identity and both bounds.
\end{proof}

\subsection{Dual-Budget Representation Planning}

For requirement $j$, let $C_j$ contain server-executed raw, projected,
aggregate, or generalized candidates with exact effect
$E_c=\langle E_c^r,E_c^i\rangle$. The request declares a nonempty required
output-name set $A_j$. After execution, candidate $c$ has observed output schema
$O_c$ and a server-observed truncation bit $\tau_c$. The fixed online utility
profile is
\begin{align*}
q(c)&=|A_j\cap O_c|/|A_j|,\\
a(c)&=q(c)(1-\tau_c),\\
u(c)&=\tfrac12(a(c)+q(c)).
\end{align*}
The caller supplies plans and the output contract, but no cost, utility scalar,
or weight. With root history $K_T$, the selector solves

\begin{align}
\max_{S}\quad &\sum_{c\in S} u(c) \\
\text{s.t.}\quad &|\left(\bigcup_{c\in S}E_c^r\right)\setminus K_T^r|\leq B^r_{\mathrm{remaining}},\\
&|\left(\bigcup_{c\in S}E_c^i\right)\setminus K_T^i|\leq B^i_{\mathrm{remaining}},\\
&|S\cap C_j|\leq 1\quad\forall j.
\end{align}

Candidate cardinalities are deliberately not added. For example, if candidates
for two requirements both add only fact $f$ and the budget is one, their joint
cost is $|\{f\}|=1$ and both remain feasible; the additive proxy
$|E_{c_1}|+|E_{c_2}|=2$ would incorrectly reject them. The public V1 scalar
planning path has therefore been removed; non-V2 planning calls fail closed.

The implementation subtracts root history, assigns remaining fact hashes dense
integers, and represents each set as a release/influence bit vector. It expands
one requirement at a time using bitwise OR and popcount. A state can dominate
another only by release-set inclusion, influence-set inclusion, and no lower
utility; comparing cardinalities alone is unsound because future candidates may
overlap the larger set. If frontier size before group $j$ is
$H_{j-1}$ and the group has $m_j$ candidates, the current pairwise dominance
implementation takes
$O(\sum_j(H_{j-1}(m_j+1))^2)$ time and $O(\max_j H_j)$ memory. Worst-case
frontier size is exponential; V2 therefore limits calls to a small
representation catalog.

\begin{theorem}[Planner optimality]
For fixed executed candidate effects and outputs, required-output contracts,
root history, and budgets, the V2 selector returns maximum utility under the
profile above among all feasible choices with at most one candidate per
requirement.
\end{theorem}
\begin{proof}[Proof sketch]
For each requirement the frontier enumerates skipping it or choosing each one
of its candidates. Every state stores the exact two set unions. Inclusion-based
pruning removes a state only when another uses subsets in both dimensions and
has no lower utility, so every optimal continuation is retained or replaced by
a no-worse continuation. Induction over requirements proves optimality.
\end{proof}

\section{System Realization}
\label{sec:system}

The prototype is implemented in Go with separate control and business
PostgreSQL 16 databases. A logical catalog declares reporting views, mandatory
scopes, stable snapshots, entity keys, allowed operations, approval routes, and
resource/exposure profiles. Startup and per-query attestation bind datasource
identity, database, role, PostgreSQL major version, ordered view schema, and
normalized view definitions.

Agents use MCP tools to list products, request a task, execute a structured
plan, inspect both budgets, invoke the representation planner, delegate a
narrower task, and retrieve results or receipts. An external approval adapter
signs the immutable grant. Arbitrary direct SQL remains available only for
legacy resource-only grants; it fails closed when exposure evidence is
required. \code{plan_exposure} accepts only V2 QueryPlans and required-output
contracts; it executes candidates before deriving their FactSets and utility.

The control schema stores one dual ledger per root, per-query reservations, and
immutable fact identities. The primary-key and check constraints are backed by
application transactions and update/delete rejection triggers. Result rows are
encrypted with AES-GCM; audit events form a hash chain. These mechanisms are
orthogonal to exposure semantics but make settlement and later verification
observable.

\section{Finite-State Analysis}
\label{sec:formal}

The split TLA+ model \code{ExposureLedger.tla} contains one root, one child, two
requests, two facts in each ledger universe, both limits set to one, and one
terminal replay. Its transitions are reserve, execute/buffer, derive,
settle, over-budget reject, pre-execution release, replay, and root revocation.
It checks dual-budget safety, exact novel charge, no delivery before settlement,
no charge without settlement, buffered rejection, evidence/buffer agreement,
non-overlapping novel charges, task-family non-amplification, and at-most-once
physical execution for delivered requests.

Using pinned TLC 1.7.1, the provenance-checked run generated
\ExposureFormalStates{} states, found \ExposureFormalDistinct{} distinct states,
and reached depth \ExposureFormalDepth{} with no invariant error. Model,
configuration, and raw-log digests are validated before this manuscript builds
\cite{lamport2002specifying}.

This is exhaustive only for the submitted finite configuration. The model
assumes exact fact derivation, abstracts SQL bytes and cryptographic hashes, and
does not mechanically prove that Go/PostgreSQL refines TLA+. The repository
therefore includes an action-to-method-to-transaction-to-test refinement map
rather than claiming a proof that does not exist.

\subsection{RQ5: Externally Scored Agent Tasks}

Planner correctness alone does not measure usefulness, so we replay a separate
agent-task corpus with 24 database-analysis objectives crossed with five
release/influence budget and history profiles (\RQFiveAgentTasks{} traces).
Each trace has four answer requirements and eight candidate representations.
The exact and utility-greedy policies receive the same candidate utility
evidence and budgets. An external scorer then ignores those utility values and
compares only the selected answer-token payloads with gold assertions; success
requires at least two of three gold assertions for every requirement.

Exact planning succeeds on \RQFiveExactSuccess{}/\RQFiveAgentTasks{} traces
(60\%) versus \RQFiveGreedySuccess{}/\RQFiveAgentTasks{} (40\%) for greedy,
and mean answer completeness is \RQFiveExactCompleteness{} versus
\RQFiveGreedyCompleteness{}. Removing root history from the exact policy reduces
success to \RQFiveNoHistorySuccess{}/\RQFiveAgentTasks{}. All three policies
have zero budget violations. The shared-fact budget-one counterexample and 500
set-valued brute-force instances provide algorithmic correctness evidence; the
trace campaign supplies the separate task-level utility measurement.

\subsection{Reproducibility Boundary}

The performance result is a controlled single-host microbenchmark on the
bundled ten-row travel fixture, not a TPC-H/TPC-DS or production-scale claim.
The agent campaign is a deterministic tool-policy replay, not a comparison of
live language models or prompts. Source-controlled reports bind the environment,
corpus, code, raw-result and sample digests. These boundaries limit external
validity but no longer leave RQ4 or RQ5 unmeasured within the stated scope.

\section{Limitations and Threats to Validity}
\label{sec:limits}

\textbf{Semantic scope.} The model accounts positive explicit disclosure. It
does not measure facts inferred from empty answers, ordering, correlations,
background knowledge, or timing. It is not differential privacy and should be
combined with a privacy mechanism when those threats matter.

\textbf{Query scope.} The executable algebra includes join and union, but the
online compiler supports one product with projection, filtering, ordering,
limit, grouping, and four aggregates. \code{AVG}, windows, negation,
difference, recursion, arbitrary subqueries, and cross-source plans fail closed.

\textbf{Identity trust.} Stable entity keys and snapshot labels are
administrator declarations. Schema attestation cannot prove uniqueness or that
a snapshot was advanced after data changes. Production use requires a
versioned publication or CDC pipeline and collision/security review for the
chosen hash and serialization profile.

\textbf{Cost.} Exact source sets can be large, root-ledger locking can become a
hot spot, and immutable history grows monotonically. Compression, sketches,
partitioned settlement, retention, and audited deletion are open design points;
approximations would require new safety semantics.

\textbf{Planning evidence.} Candidate costs, effects, and scalar utility are
server generated. The online utility profile measures required-output coverage
and truncation, not semantic answer truth; its output contract is caller declared
and receipt bound. The gold-answer trace scorer measures the consequence of
selection independently, but does not test model-generated candidates.
Production still needs an approved semantic task contract and live-agent
evaluation.

\textbf{Deployment.} The prototype has one gateway instance, static local
tokens, an in-memory approval demo, and one PostgreSQL connector. It lacks a
distributed execution lease and centralized key custody. The measured
single-host fixture does not establish multi-node scaling or production SLOs.

\section{Conclusion}

Task-bound authorization answers what an agent may query; task-bound exposure
accounting additionally constrains what its entire delegated workload may
accumulate. \system realizes that distinction with stable facts, separate
release and source-influence sets, same-snapshot provenance, atomic novel-fact
settlement, and an exact dual-budget representation planner. The current
artifact establishes a coherent semantic and systems foundation, finds no
violation in a finite ledger model, and observes zero mismatch across 1,024
unique PostgreSQL rewrites. The full path has 12.1-ms p50 latency at one worker
and exposes root-ledger serialization at higher concurrency. Exact planning
improves externally scored trace success from 40\% to 60\% under matched
budgets. These empirical results answer RQ4 and RQ5 for the declared local and
deterministic scope; TPC-scale, multi-node, and live-LLM generalization remain
outside the claims.
